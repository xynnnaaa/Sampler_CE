# TPCH-skew 采样日志性能分析

数据来源：`../runfile_time/log_worker_0.log` 至 `log_worker_9.log`。完整扫描 35,303 行日志，共 164 个不同 join template、164 个 Bitmap 报告，均标记 complete，worker 分配数与完成数一致，未发现异常记录。

汇总仅使用 template 报告；Bitmap 与 template 统计覆盖同一段工作，不能重复相加。占比为总阶段耗时 / 总 template 耗时，而不是各模板百分比的简单平均。各 template 的 exclusive 分项之和与 wall 的最大差仅 0.0005 秒（日志舍入误差）。

**核心结论：anno 位图翻译与缓存写入占 77.67%，是绝对主瓶颈。** 163/164 个模板的最大 exclusive 项都是它；每个 worker 的该项占比均在 75.78%～79.81%。

累计 template 墙钟时间为 368,794.44 秒（102.44 worker-hours），不是实际单次运行的历时，也不是 CPU 使用时间。十个 worker 并行计时重叠。如果同时启动，最长 worker 的 43,305.06 秒（12.03 小时）决定整体完成时间。模板耗时中位数 2343.30 秒，均值 2248.75 秒，最大 4,708.73 秒。

## 放大耗时的工作量与实现

累计翻译 1,509,722,689 行 anno；当前 `_translate_pid_bitmap` 对整个位图中每一个 1 执行 Python 循环和 pid_map 查找，即使该 PID 不属于当前模板，仍会扫描并查询。它不只处理当前模板需要的 PID。既有 create_anno.log 记录 lineitem 有 10,507 个 PID、partsupp 有 8,823 个 PID，其余大表约 3,733～4,229 个。日志只能定位翻译与缓存写入的整体开销，未拆开 find 循环、字典写入和内存/调度等待，不能断言其中某一项精确占多少。

全局缓存请求统计：459,920,881 次命中、1,509,722,689 次未命中，按每次调用内去重后的 ID 计数，命中率 23.35%。这不是全库唯一行数；同一真实表行跨模板、跨别名可以被重复翻译。当前缓存的是模板专属 QID 掩码，每个模板清空，不能直接保留到下一模板继续使用。

Root Top-K 后共 9,529,792 个候选，复制出 952,979,200 条初始路径，等于每候选 100 条。所有单步扩展累计处理 3,291,323,648 条输入路径，输出/输入之比 97.77%（跨步汇总，不是完整路径成功率）。原表邻居查询累计取回 12,411,667,908 行，平均每次邻居查询约 122,923 行。候选数量和查询/翻译工作量的放大，是复杂模板耗时高的重要结构性原因。

纯随机阶段：8,989 次尝试、8,287 次成功，成功率 92.19%，总耗时 369.11 秒。暂不应优先优化它。

## 覆盖收益递减

8,046 条有耗时和 Coverage 输出的分区记录中，1,998 条相对此前分区没有新增覆盖（24.83%），累计 84,486.43 秒，占 template 总耗时 22.91%。这里只统计有输出的分区；某些 continue 分支没有分区计时日志。零新增覆盖仍可能输出 join 样本，对样本多样性有意义，不能视为完全无用，也不能把这段时间全部作为可无损省掉的时间。

分区 26～50 的 3,986 条记录中，1,521 条没有新增覆盖，其耗时 62,428.31 秒。覆盖分区结束时，逐模板覆盖比例的中位数约 62.97%；随机阶段没有更新覆盖统计，因此不能当作最终全部样本的真实覆盖率。

worker 5 首个六表模板：分区 24～45 始终停留在 20/35，仍执行数十秒一次的采样；最终为 21/35。该模板总计 3,347.72 秒，其中翻译占 64.13%、anno execute 占 22.27%。

## 建议的优化顺序

1. **先优化 PID→QID 翻译。** 为每个 alias 预编译当前模板相关 PID 的位置与 QID 掩码，只读取相关位；可比较直接字符串索引和在 C 层解析为整数后先与相关 PID 掩码取交集的实现。必须保持 PostgreSQL 字符串左侧位置与整数 bit 位的对应关系，不能按旧 PID 位置直接套整数位移。无相关 PID 的 alias 可直接返回 global_map。该建议来自代码与日志的推断，尚无优化后实测。
2. **减少待翻译与扩展的路径。** acc_bmp 已经不能覆盖 uncovered 查询时，后续 AND 无法恢复覆盖，可从覆盖候选搜索中提前剔除。需保留分区没有正覆盖候选时的随机回退，避免改变当前样本填充行为。其次试验按 root 潜力/历史增益调整 w_samples、Top-K 和停滞后切随机策略；这些会影响候选搜索与覆盖结果，应同时比较覆盖率和耗时。
3. **减少 anno 查询的数据量和 Python 对象开销。** 当前读取完整 query_anno::text，若只需模板内位，可考虑投影相关位或更紧凑的传输；先做局部性能验证。跨模板复用原始 PID 位图不同于复用 QID 缓存，要限制内存容量。
4. **邻居端减少全量物化。** 当前查回所有邻居、转字符串和字典后才随机选一行，累计 124 亿返回行。考虑缓存可复用的邻接信息、紧凑元组/索引结构，或数据库端按连接键随机取候选；需验证每条路径独立、均匀随机选择的语义，不能简单把一个键的所有路径绑定到同一个邻居。
5. **优化路径存储与调度。** 用更紧凑的路径状态替代频繁字典复制；动态任务队列或按历史耗时分配模板。更多 worker 是否有益需要 CPU、RSS、I/O 和数据库等待数据，当前日志不足以判断。

仅翻译阶段提速的静态估计（其他时间固定）：2 倍→整体约 1.63 倍；5 倍→2.64 倍；10 倍→3.32 倍；完全消除该项的理论上限约 4.48 倍。这不是对实际运行的承诺；优化后邻居查询、anno SQL、路径更新及并发资源竞争会成为更明显的瓶颈。
