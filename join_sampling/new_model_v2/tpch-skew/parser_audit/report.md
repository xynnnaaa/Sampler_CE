## 结论

- 全部 44,118 条查询进入检查，无解析异常、表名/别名映射异常或不连通 join graph。
- 原始查询按列等价类计算得到 164 个模板；V2 得到 164 个模板。
- 模板签名不一致、错误合并、错误拆分均为 0；同一表对多个连接条件被覆盖、连接条件遗漏也均未出现。
- 所有模板生成的执行计划，其连接等价类与完整 join graph 一致；这份数据没有生成树丢失独立连接约束的问题。
- 原始 WHERE 原子条件类型只有 EQ（233,150 次）、GTE（22,475 次）、LT（33,848 次）。除字面量大小写外，过滤条件结构没有遗漏或变化。
- **32,057 条查询（72.66%）发生字符串字面量变化，共 53,616 个字面量。** 因此不能认为谓词语义正确。

## 根因与示例

V2 通过项目共用的 `mscn/query_representation/utils.py` 中 `extract_join_graph()` 解析 SQL。第 1422 行 `sql_str = sql_str.lower()` 会同时改动标识符和字符串字面量。

第一条查询的实际变化：

| 原始条件 | 当前解析结果 |
|---|---|
| `tpch_p.p_brand = 'Brand#35'` | `tpch_p.p_brand = 'brand#35'` |
| `tpch_c.c_mktsegment = 'MACHINERY'` | `tpch_c.c_mktsegment = 'machinery'` |

第 4 条查询还会将 `'AIR'` 转成 `'air'`。这些变化在通常大小写敏感的文本比较下改变查询语义。当前无法连接配置中的数据库，未确认该库实际列类型、排序规则与字符串值，不能把受影响数量等同于已证明结果错误的查询数量。

错误在解析阶段已经写入 `global_pid_to_pred`，后续内存 QID SQL 会直接使用这些值。缓冲区表示或位序本身不会纠正它。此问题是 V1 共用解析器的既有问题，V2 沿用了它；此前的 V1/V2 一致性测试不能替代针对原 SQL 的语义验证。

## 修改建议

单独修复解析器的字面量大小写问题：按原 SQL 解析，仅归一化需要归一化的标识符，保留字符串值，并注意带引号标识符的大小写语义。可在 V2 使用独立解析入口，避免直接影响旧流程。本次检查没有修改采样代码或共用解析器。

OR/NOT/BETWEEN/显式 JOIN、多条件表对等通用解析限制在这份文件中没有触发，不能据此认定解析器能够处理其他 SQL 形式。
