读取 runfile 下全部 10 份日志，共 294,495 行；1,236 个 template 全部完成，与各 worker 的 assigned 数一致。未发现 Error/Traceback/failed。累计 template 时间 100,669.6163 秒 = 27.9638 worker-hours。

## 达到累计 10 小时的预算

当前可拆成 annotation.prepare 13.989 小时、root clone + coverage walk 13.084 小时、其他 0.891 小时，三者不重叠。annotation 准备全部消除也只到 13.975 小时。达到 10 小时需要整体约 2.80 倍加速、减少约 64.24% 时间。

一个可验证的目标组合：annotation 4 倍加速（3.497 小时）+ root clone/coverage walk 2.5 倍加速（5.234 小时）+ 其他保持 0.891 小时 = 9.622 小时。该组合是预算目标，不是已测性能承诺，各阶段并发资源相互影响。

## 建议实施顺序（采样参数及选择规则保持不变）

1. 先验证已经实现的 dense 取消排序及元数据缓存，避免把旧运行估计当成新运行实测。元数据原占 0.75%，排序成本未单独测量。
2. 路径更新先尝试原地修改私有 path/vals，去掉每一步重复 copy；检查引用生命周期。后续把固定列映射为 slot，使用紧凑数组及共享只读 root/邻居行，而不是每条路径复制包含字符串键的字典。保持候选顺序、random.choice 调用顺序、路径顺序、并列最高分首个胜出规则。
3. 大表采用按实际选中 ID 批量获取 QID，并在当前 template 内缓存；保留同样的候选邻居及随机选择。Root 访问广时保留全量模式，非 root 大表先实验按需模式。当前 lookup_ids 只是每批去重后的累计数，不能拿它直接计算全 template 命中率，需另测各 alias 的唯一 ID 数及重复比例。
4. 若同表谓词组合高度复用，按 table+predicate+数据版本缓存每行 1 bit 的命中向量，跨 template、worker 用只读 mmap 共享。QID 排列仍每 template 独立。新谓词分批评估、批量 pack，当前 template 的 QID 矩阵分块向量化组装或仅选中 ID 组装，避免逐行遍历全部全局 PID。所有首次构建成本计入 10 小时目标，设置容量上限和单生产者协调。cast_info 每谓词 4.321 MiB，1,000 个谓词约 4.22 GiB。
5. 全量路径可试 COPY (query) TO STDOUT (FORMAT BINARY) 返回实际 bit varying，去掉 ::text 和逐行字符串转 int 再转 bytes。PostgreSQL 二进制 bit 串格式、位序及 ID 位宽要专门处理；避免改用 fetchall 把全表结果装入 Python 内存。

PostgreSQL 官方参考：[COPY 二进制格式](https://www.postgresql.org/docs/17/sql-copy.html)、[DECLARE CURSOR 不采用 parallel plan](https://www.postgresql.org/docs/17/when-can-parallel-query-be-used.html)。COPY 能避免这个游标限制，但不保证并行或倍数收益，须检查实际计划与 10 worker 竞争。

分析产物：summary.json 包含完整逐 template 记录与阶段、计数器、worker 汇总；templates.csv 按总时间降序。predicate_reuse.json 若生成，记录用当前解析器读取完整工作负载的谓词跨 template 复用统计。未修改采样实现或发起新一轮采样。
